# Lens pilot, run 2: three arms on gpt-5.6-luna

Run 2026-09-23 on the mini. gpt-5.6-luna through OpenRouter, lemans 1.3.1,
host-side miniswen, docker backend, upstream trial limits. Writebook stage 1:
22 tasks, 5 attempts per task, three arms. 330 trials, $4.86 total.

Arms:

- **baseline**: the tasks as published.
- **lensed**: `lens/SKILL.md` (15 items, 13 Rails API identifiers) framed as
  a loaded Agent Skill ahead of each task.
- **vocab**: `lens-vocab/SKILL.md`, the same 15 items with every API
  identifier rewritten as a plain description. Same trigger conditions, same
  order, 953 words against 897.

Replication check: the Foundation's own luna run on these tasks scored 49/66
(74%), 14 steps, $0.014 a trial. Baseline here: 75/110 (68%), 14 steps,
$0.014 a trial. Same harness, same model, same corpus, inside noise.

## Headline

| | baseline | lensed | vocab |
|---|---|---|---|
| trials solved | 75/110 (68%) | 77/110 (70%) | 73/110 (66%) |
| pass@5 | 19/22 | 19/22 | 18/22 |
| reach (anchored tasks, 105 trials) | 41/105 (39%) | 45/105 (43%) | 46/105 (44%) |
| reach given pass | 40% | 42% | 44% |
| cost | $1.57 | $1.71 | $1.59 |

Three arms within four trials of each other on pass, within five on reach.
The lens does not move what luna ships on Writebook. The vocabulary control
lands on top of it, so the run 1 story (reach moves where the lens names an
API) does not survive on a model that already knows the API names.

Three tasks fail 0/5 in every arm (ar-erase-account, as-purge-embedded-images,
as-variant-processed-once). Fourteen tasks are within one attempt of each
other across all three arms. The five that moved by two or more:

- ar-bulk-access-grants: baseline 4/5, both checklist arms 1/5. The only
  large effect in the run, and it is negative, and it is the same in lensed
  and vocab. Item 5 of the checklist warns about `insert_all` bypassing
  callbacks and validations; the task wants `insert_all`. Reach stayed 5/5
  in all arms, so the agent used it either way and then did something else
  wrong. Read all 15 trajectories (2026-09-23, Minerva): nine of the ten
  checklist failures and the one baseline failure die on the same assertion,
  `a conflicting roster reports the first conflicting grant's position`
  (expected 0, got 1: a duplicate at index 0 ahead of an unknown level at
  index 1). The agent hoisted the level check into its own pre-pass ahead of
  the duplicate pass, so the wrong bad row wins; two lensed trials went
  further and made that pre-pass `raise ArgumentError`, which turns four
  tests into errors (5/9). Baseline passers check the level too, but inside
  the same roster-order pass (`[invalid, duplicate].compact.min` or one
  `||`), which is what the instruction's "rejected like any other bad row"
  asks for. Item 5 ("verify that skipping validations is intentional and
  noted") frames validation as a distinct upfront concern, and the agent
  obliges by structurally separating it; the vocab wording says the same
  thing without naming `insert_all`, which is why both arms land on 1/5.
  So the effect is the guidance's semantics, not the API name, and it is
  the one place in the run where the checklist changed the shape of the
  code rather than the words around it.
- hw-scoped-broadcast: 3/5, 1/5, 2/5. Same direction, smaller.
- sec-audit-sweep: 2/5, 4/5, 3/5. The one task where the named-API story
  from run 1 still shows: the lens names `sanitize_sql_like`, lensed did best,
  vocab in between.
- sup-legacy-conversions: 3/5, 5/5, 4/5. Same ordering.
- aj-enqueue-after-commit reach: 3/5, 5/5, 3/5. The lens names the API and
  only the lensed arm reached for it every time. Pass was 5/5 regardless.

Read together: the two tasks the lens helps are the two whose anchor it
names, the one it hurts is the one whose anchor it warns about, and the
ordering lensed > vocab > baseline on those tasks is what a vocabulary prompt
predicts. Net across 22 tasks it cancels to nothing.

## Cost

Per trial, per arm: $0.0143, $0.0155, $0.0145. The checklist adds about a
thousand tokens to every step, which is the 8% on the lensed arm. Caching
worked throughout (OpenRouter passes OpenAI's automatic caching), which is why
330 trials cost less than four Haiku trials did in run 1.

## What this says about the lens

A pre-response checklist read as text does not change what a capable agent
ships on tasks it can already do, and it does not lift the tasks it cannot.
It nudges which API name the agent reaches for, in both directions. That is
run 1 and run 2 agreeing on a weak model and a competent one.

The next experiment is not another arm. It is the same 15 items asked as
questions over the diff by a decision model, with the answers fed back to the
agent before it submits. The lens becomes a gate instead of a preamble.
Run 1 and run 2 leave 418 diffs with verifier outcomes to test that offline
first.

## Reproduce

Config in `baseline/`, `lensed/`, `vocab/` (`bench.yml` each);
`prepare.sh` builds the three task sets from a rails/ai-evals checkout.
`lemans report --runs-dir <arm>/runs -A task` and
`ruby reach.rb baseline=… lensed=… vocab=…` produce the tables above.
