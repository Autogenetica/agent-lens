# Lens pilot, run 4: a process lens and an app lens against run 2's arms

Run 2026-10-05 on the mini, same profile as run 2 byte for byte apart from
the lens: gpt-5.6-luna via OpenRouter, host-side miniswen, docker backend,
upstream trial limits, 22 Writebook tasks × 5 attempts. Two new arms, 220
trials, $3.34. Compared against run 2's baseline, lensed, and vocab arms
(2026-09-23, same model id, same tasks, same limits).

Why these two. Runs 1 to 3 and three gate replays agreed that the Rails
Guides idiom checklist is orthogonal to why these patches fail. The
verifier checks that fail are application behaviour at the edges: a
revision's image freed too, an admin without an access row still told,
the first conflicting grant reported, exactly one derived copy. Two
corpora could carry that:

- **process**: `lens-process/SKILL.md`, shaped from the Testing Guide
  chapter alone (`corpus/rails-testing-guide.md`, 108 KB), framed as "a
  Rails engineer who ships a ticket only after every behaviour the request
  states has a test that exercises it, edge cases included." Fifteen items;
  the first three are behaviour-per-test, sad-path coverage, edge-case
  enumeration.
- **app**: `lens-app/SKILL.md`, shaped from Writebook v1.2.1 itself
  (`corpus/writebook-app.md`: schema, routes, app Ruby, views, 148 KB),
  framed as "keeping to the conventions its own code establishes." Fifteen
  items, all Writebook: `accessable_or_published` scoping, `ensure_editable`,
  the `[book, book.editable?]` cache key, `everyone_access` propagation,
  deactivate-not-delete, FTS sanitising. No task names, no canary.

The process arm is the first arm in four runs to move the pass rate: nine
trials over baseline, and the mechanism is visible in the patches. It
wrote tests in 93 of 110 trials against baseline's 50, three times the
test lines, a step and a half more per trial, 16% more cost. That is the
lens doing what it was shaped to do.

The app arm is baseline. Three more trials, same pass@5 as vocab, same
step count and cost as baseline. Knowing the app's conventions by name
did not change what luna shipped.

Process against baseline, paired by task: 8 tasks up (+13 trials), 2 down
(−4), 12 unchanged. Sign test on the ten that moved: one-sided p = 0.055,
two-sided 0.11. Suggestive at 22 tasks, not settled. The three tasks every
arm fails 0/5 did not move, and nothing was expected to move them; they
fail on behaviour the diff cannot show (an attachment purged, a variant
not reprocessed, a cascade erase).

The largest single gain is av-toc-cache-per-role, 1/5 to 4/5. Its failing
check in run 2 was "an entry edited in place still renders on its own",
which is exactly the kind of edge a test-per-behaviour discipline catches
and a convention list does not: the app lens names the very cache key the
task is about and scored 0/5.

## The one thing every lens does

ar-bulk-access-grants: baseline 4/5, every lens arm 1/5. Four different
checklists, idiom, vocabulary, process, app, and the same drop. Run 2's
trajectory read traced the failure to a validation pre-pass hoisted ahead
of the roster pass, so the wrong bad row wins. What the four arms share is
not content. It is the preamble: "Before responding to the user,
internally verify each applicable item below." That framing, on this task,
makes luna structurally separate checking from doing, in all four arms.
It is a confound for every lensed number in this pilot, bounded at about
three trials per arm, and it argues that the shaped skill's standing
header deserves its own ablation before the content does.

## What this says

A checklist about *how to work* moved the pass rate on a competent agent;
checklists about *what to know* (Rails idiom, Rails vocabulary, Writebook
conventions) did not. The failing checks were behaviours the ticket stated
and the agent did not exercise; the process lens made it exercise them,
visibly, in the test files it wrote. It cost 16% more per trial and bought
8 percentage points of pass rate, nearly all on tasks in the 2-to-4
band where the agent was close.

For agent-lens: the tool shaped a faithful checklist every time. The
question was never faithfulness, it was which corpus and which framing.
The Testing Guide with a process framing is the first pairing that
produced a lens worth loading.

## Next

- Rerun the process arm once (another $1.80) to see whether 84 holds; at
  22 tasks a second sample is cheap and the sign test is on the edge.
- Preamble ablation: the process lens with the standing header removed,
  to size the bulk-access-grants confound and see whether the gain is the
  items or the framing.
- Nothing more on knowledge lenses for this corpus.

## Reproduce

`prepare.sh` now builds five arms. `lemans report --runs-dir
<arm>/runs/gpt-5.6-luna -A task`; `ruby reach.rb baseline=… lensed=…
vocab=… process=… app=…` with the `runs/gpt-5.6-luna` subdirectories
(the arm run dirs also hold Haiku and run-3 subdirectories now). Test-file
counts are a grep over `agent.patch` for `+++ b/test/`.
